### 스킬·도구 개선 후보(내일 판단)

1. render가 표 세로 스크롤바와 넘친 행을 잡지 못한다. Haiku 이력 표는 점검 0건인데 마지막 행이 잘렸고, Opus도 18행에서 `참고:` 줄이 나오지 않았다고 보고했다. 점검 추가 여부를 정해야 한다(규칙을 점검으로 옮길지는 `docs/1124.md`의 A/B 기준을 따른다).
2. 고정 높이 `Titled` 칸의 제목 줄 높이를 알 수 없다(Sonnet·Opus, 지난 언어 A/B에서도 나옴).
3. 행 수가 다른 고정 표 두 개를 나란히 두면 아래가 빈다(Sonnet 지적, Haiku 결과물, 지난 A/B에서도 나옴).
4. dialog `SetFooter`에 비활성 이유 Caption을 둘 자리가 없다(Opus, 지난 A/B에서도 나옴).
5. 체크박스 대용이 없어 단계 완료를 콤보로 받는다. 그래서 사용자가 dialog 안에서 조건을 직접 바꿔 Release를 풀 수 있다(Sonnet·Haiku). 지침에 "선행 조건은 데이터에서 받고 dialog에서 바꾸게 하지 않는다"를 넣을지 정해야 한다.

### 검토할 질문: 테스트를 Sonnet으로만 해서 Sonnet에 맞춰졌나?

배경: 스킬은 Opus가 썼고, 확인 시연(r1~r5, 1124~1126 회차)은 계속 Sonnet으로 돌렸다.

**영향이 있을 수 있는 이유**
- "Sonnet이 막힌 곳 → 규칙 추가 → Sonnet으로 다시 확인"을 반복하면 규칙의 내용, 표현, 상세함의 수준이 Sonnet에 맞춰진다. Sonnet이 원래 잘하던 곳에는 규칙이 없으므로, 다른 모델이 그곳에서 틀리면 지침이 비어 있게 된다. Haiku의 OCAP 단계 누락과 표 마무리 부족이 이 경우일 수 있다.
- 이번에 Sonnet의 도구 호출(18회)과 출력 토큰(31k)이 가장 적었다. 지침이 안내하는 경로와 Sonnet의 습관이 맞아 헤매지 않은 결과로도 읽힌다.

**그것만으로는 설명되지 않는 점**
- 품질은 Opus가 더 높았다(19 대 16). Sonnet에 과하게 맞춰졌다면 Sonnet의 품질이 가장 높아야 자연스럽다.
- 세 모델 모두 같은 지침 빈틈을 지적했다(`Titled` 높이, 표 나란히 배치, dialog 푸터, 체크박스). 모델과 상관없는 스킬 자체의 문제다.
- 반대 방향의 편향도 있을 수 있다. 지침을 쓴 모델이 Opus라서, Opus가 자기 식 표현을 가장 잘 읽었을 수 있다.
- 빠르고 토큰을 적게 쓰는 것은 Sonnet이 원래 가진 성격일 수 있다. 실행이 1회뿐이라 실행마다 생기는 편차와도 구분되지 않는다.
