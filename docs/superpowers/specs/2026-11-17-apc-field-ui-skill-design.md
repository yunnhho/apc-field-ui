# APC Field UI Skill — Design

Written: 2026-11-17 · Status: awaiting review

## 1. Intent

When an agent builds a new customer field program (WinForms), make it build screens **to the APC.UI baseline from the start**.

This repository's `CLAUDE.md` is not read automatically from other project folders. Without a skill the agent does not know APC.UI exists and builds screens with standard WinForms. Even when told about the repository, its exploration differs every time and it misses rules (status colors, protecting the default theme). The skill's primary effect is **baseline compliance and consistent results**. Handing repetitive work (skeleton, API discovery, render) to scripts to cut tokens and failure rate is the secondary effect.

Invocation scene: in a new project folder, the user asks "build a screen like this."

## 2. Goals / Non-goals / Anti-goals

**Goals**
- Personal skill `~/.claude/skills/apc-field-ui/SKILL.md`
- On request, build a **screen shell** with sample data and an **interface slot** for data connection.
- Work that must be identical every time (skeleton creation, API discovery, render check) is done by repository scripts. The agent focuses on layout decisions.

**Non-goals**
- No real PLC, DB or serial connection code.
- No procedure for migrating legacy screens to APC.UI. (Taking captures as input is in scope; see §5.2.)
- No .NET 6/8 builds. No plans to use them.
- No plugin or MCP wrapping. Wrap it when team distribution is needed.
- No VS designer support. Screens are laid out **in code only**, like the templates (layout in the constructor, scaling with `S()`).
- No navigation frame across multiple screens. A new program is **one main screen + dialogs** by default.

**Anti-goals** (counted as failure even if it works)
- Screens drawn directly with standard `Button`, `DataGridView`, etc.
- Changing the hue of status colors (run/warn/alarm/stop/info)
- Modifying `themes/default` or the repository's `assets-src/*.svg` (shared sources) for a customer request
- Writing control APIs by hand in the skill document. It starts drifting from the repository.

## 3. Constraints

- New projects must be **.NET Framework 4.x WinForms** only. Otherwise (.NET 6/8, WPF, web) the skill stops and explains why.
- New project code follows **the new project's own** `TargetFrameworkVersion` and `LangVersion`. The C# 7.3 constraint applies only to APC.UI internals. Do not pin 7.3 in the skill.
- Repository constraints stay: .NET 4.0 / C# 7.3, no NuGet additions, `./build.sh` → `ALL PASSED`.
- One source of truth: the repository. The skill only points to the repository path (`C:\00P_PGDesignReference`) and keeps no copy of its contents.

## 4. Approaches considered — **B chosen**

| | Description | Verdict |
|---|---|---|
| A. A single SKILL.md | On every call the agent reads the sources and writes skeleton and render scripts itself. | Gets the compliance effect, but repeated cost is high (est. 25–35k tokens) and quality varies per call (e.g. hand-written .NET 4.0 old-style csproj breaking). |
| **B. SKILL.md + repository scripts** | Skeleton creation, auto-generated API summary and render handled by scripts. | **Chosen.** Cuts repeated cost to an est. 5–8k tokens and makes results deterministic. The price is 2–3× the repository work of A. |
| C. Plugin / MCP | Package B. | For a single user today, same efficiency as B with more to maintain. |
| (excluded) dotnet `new` template | | Does not fit .NET Framework 4.0 old-style projects well. |

Why distribution stays as a dll reference: using WinForms custom controls from the VS designer toolbox needs a compiled assembly. Copying sources makes every project diverge.

## 5. Design

### 5.1 Repository changes

| # | Change | Details |
|---|---|---|
| 1 | Move `TemplateView` into the dll | Move `src/APC.UI.Demo/Templates/TemplateView.cs` (internal) to a public class in `src/APC.UI`. It includes the header bar + body + alarm bar frame and helpers such as `S()` and `Caption()`. The 7 demo templates inherit from it. The gallery must look the same as before. With no designer support, keep the existing `protected TemplateView(string title)` constructor. |
| 2 | dll version rule | Bump `AssemblyVersion` (currently 1.0.0.0) when the public API changes, so a dll copied into a project can be dated. Add the rule as one line in the repository `CLAUDE.md`. |
| 3 | Tool console `src/APC.UI.Tools` | One .NET 4.0 console app with two commands.<br>· `api <dll> <out.md>`: extracts public types and members (properties, methods, events, with XML summary comments) to Markdown via reflection.<br>· `render <assembly> <type name> <themeDir> <out.png> [--size 1920x1080] [--compare <original.png>]`: after `ApcTheme.Load`, draws a `UserControl` or `Form` off-screen and saves a PNG. With `--compare` it also makes a side-by-side comparison with the original. |
| 4 | `docs/api.md` | Regenerated by `build.sh` after every build with `APC.UI.Tools api`. dll version at the top. Committed. |
| 5 | `tools/new-project.sh` | Creates a new project skeleton (§5.3). |
| 6 | Extend `build.sh` checks | In a temp folder create a project with `new-project.sh` → build → `render` the default screen and confirm a PNG comes out. If this fails, `ALL PASSED` is not printed. |
| 7 | Fix `render-assets.mjs` | It only processes names present in the default folder, so new names that exist only in the `--override` folder (`icon_*` etc.) are silently skipped. Render those too. |

### 5.2 Skill flow (`SKILL.md`)

1. **Check input**
   - Required: **purpose** (monitoring: whole process line / sensors attached to equipment, etc., or process equipment program: Failure Analysis, etc.), **main function**, **whether there are detail dialogs**. Ask only for what is missing; if everything is there, proceed.
   - Optional: captures of the old program, customer requirement file, extra detail requests. With a requirement file, complete the main function list from it.
2. **Check and prepare the project**
   - No csproj → create one with `new-project.sh`.
   - A csproj exists → confirm it is .NET Framework 4.x WinForms, otherwise stop. If it is, add only the dll, theme and shared files with `new-project.sh --into-existing` (§5.3).
   - Read the new project's `LangVersion` and apply it to the code that follows.
3. **API discovery**: read `docs/api.md`. Read only 1–2 chosen template sources for layout reference.
4. **Layout decision**
   - If an existing template fits the purpose, follow its layout.

     | Purpose | Starting template |
     |---|---|
     | Monitoring (whole line, equipment status) | `EquipmentView` |
     | Monitoring (sensor value trends) | `TempHumiView` |
     | Process equipment program (analysis, judging) | `FailureAnalysisView` |
     | Work input (start, production, defects) | `WorkStartView`, `ProductionView`, `DefectView` |
     | Lookup | `HistoryView` |

   - If the purpose is unclear or there are extra requests, compose a **new layout from existing controls** on the `TemplateView` frame.
   - With a capture, keep the original's information layout (what is where) and change only the look to the APC.UI baseline.
   - Detail dialogs are separate forms based on `ApcDialog`; put `ApcDialog.Confirm` before irreversible actions.
5. **Only when new artwork is needed**
   - Create the SVGs in **the new project's** `assets-src/` following the existing file name rule (`{btn|lamp|win|icon|logo}_{name}_{state}`). The repository is not touched, so no repository git/branch handling is needed.
   - Generate PNGs with `node <repo>/tools/render-assets.mjs --out <new project>/themes/<customer>/assets --override <new project>/assets-src`.
   - Art replacing an existing name is used by the controls automatically. Art with a new name is loaded with `ApcTheme.GetImage`.
6. **Data slot**: one `IMainViewSource` interface for the main screen and one `SampleMainViewSource` sample implementation. Screen code depends only on the interface. Dialogs receive the values they need from the main screen and have no data interface of their own.
7. **Done check**: new project builds → `render` PNGs of the main screen and each dialog → show them to the user. If a capture was given, also show the `--compare` image.

### 5.3 `tools/new-project.sh`

```
tools/new-project.sh <target folder> <project name> <customer> [--framework v4.0] [--into-existing]
```

When creating a new project it generates:
- `<project name>.sln`, `<project name>.csproj` (old-style, WinExe, the given `TargetFrameworkVersion`, references `lib\APC.UI.dll`)
- `Program.cs`: `ApcTheme.Load(@"themes\<customer>")`, `ThemeException` handling, runs `MainForm`
- `MainForm.cs` (inherits `ApcForm`), default screen `Views/MainView.cs` (inherits `TemplateView`)
- `Data/IMainViewSource.cs`, `Data/SampleMainViewSource.cs`
- `app.manifest` (`dpiAware`)
- `lib/APC.UI.dll`: built in Release from the repository and copied.
- `themes/<customer>/`: copies the repository's `themes/<customer>` if it exists, otherwise `themes/default`. After copying, the customer theme is managed **in the project**. The theme folder is registered in the csproj to copy to build output.

With `--into-existing`:
- Supports **old-style csproj only**. For SDK style it stops and explains why.
- On the first run it adds `lib/` and `themes/` and adds the reference and theme copy items to the existing csproj (no duplicates if already present). No other files are created.
- Rerun in a project that already has APC.UI → only `lib/APC.UI.dll` is replaced with the new version. The theme is not overwritten since the project may have changed it. This is the update path for the §5.1-2 version rule.

## 6. Left to the implementer

- `api.md` formatting details (member order, how much inherited-member output to omit)
- How `render` handles controls `DrawToBitmap` cannot draw
- SKILL.md wording and description trigger sentences. Keep the body short and point to `docs/api.md` for the API only.
- Script option names

## 7. Verification

- `./build.sh` → `ALL PASSED`. Includes existing checks, `api.md` generation, and the new-project → build → render check.
- Gallery run: the 7 templates look the same before and after moving `TemplateView`.
- Skill trial: in an empty folder, invoke with "equipment monitoring screen, main function: running status per line, no dialogs" and confirm it reaches a build and PNGs. Run the same request once without the skill and compare (baseline compliance, tokens).
